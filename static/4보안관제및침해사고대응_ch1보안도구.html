Q13회

[패킷 캡처]는 웹 스캔 공격을 당하고 있는 시스템으로 전송되고 있는 트래픽 중 하나를 캡처한 결과이다. IPS(침입방지시스템)에서 이 사이트로 전송되는 패킷의 내용을 검사하여 "/admin"란 문자열이 포함된 경우, "Web Scan Detected"란 메시지를 로그로 남기기 위한 Snort Rule을 작성하고자 한다. 작성된 [Snort Rule]의 밑줄에 들어갈 키워드를 쓰시오.

답과 해설 보기

답: ① 80　② content　③ msg

  • Snort Rule 헤더 형식
<Action> <Protocol> <SrcIP> <SrcPort> <Direction> <DestIP> <DestPort>
항목값
<Action>alert
<Protocol>tcp
<SrcIP>any
<SrcPort>any
<Direction>->
<DestIP>10.0.0.25
<DestPort>80
  • 패킷 캡처 화면에서 Protocol이 HTTP이므로 목적지 포트는 80을 설정
  • msg
    • 탐지 시 출력할 메시지 지정
    • Snort에서 Rule에 대한 정보제공을 위해 사용되며, 탐지에 영향은 없음
    • 예: msg:"SQL injection attempt";
  • content
    • 페이로드에서 특정 문자열 패턴이 있는지 검사
    • 기본적으로 대소문자를 구분함
  • 해당 사이트로 전송되는 패킷의 내용을 검사하여 "/admin"란 문자열이 포함된 경우, snort rule을 동작시키므로 옵션 중에서 content를 설정
  • 문자열 패턴을 탐지할 때 출력하는 메시지인 "Web Scan Detected"란 메시지가 나오므로 msg를 설정
Q27회

다음 Snort Rule은 10번째 바이트부터 4바이트 범위에 "ABCD"라는 ASCII 문자열이 있는지 검사하기 위한 룰이다. 밑줄 안에 들어갈 명령어를 쓰시오.

alert tcp $EXTERNAL_NET any -> $HOME_NET any (msg:"Check ABCD String"; ( ① ):"ABCD"; ( ② ):10; ( ③ ):4; sid:1100002;)
답과 해설 보기

답: ① content　② offset　③ depth

  • 패킷의 10번째부터 4바이트 범위에 정확히 'ABCD'라는 문자열이 있으면, 'Check ABCD String' 메시지와 함께 경고(alert)를 발생시킴
  • snort의 Body 부분의 Option
    • msg — 탐지 시 출력할 메시지 지정 / Snort에서 Rule에 대한 정보제공을 위해 사용되며, 탐지에 영향은 없음
    • content — 페이로드에서 특정 문자열 패턴이 있는지 검사 / 기본적으로 대소문자를 구분함
    • offset — content 검색의 시작 위치를 지정 / 지정한 바이트만큼 떨어진 위치부터 검색 시작
    • depth — 검색 범위의 길이를 지정
  • 페이로드에서 "ABCD" 패턴이 있는지 검사하기 위해서 content를 설정
  • 10번째 바이트부터 4바이트 범위에 문자열을 검사해야 하므로 offset에서 지정한 위치부터 얼마나 많은 바이트만큼 탐색할 것인지 탐색 범위를 제한하는 depth를 설정

  • 수리카타는 기존 스노트(Snort)의 단일 스레드 방식에서 벗어나 멀티 코어 및 멀티 스레드 아키텍처를 활용하여 대용량 네트워크 트래픽을 효율적으로 실시간 분석할 수 있고, 기존 스노트와 완벽하게 호환되는 장점을 가짐
  • 수리카타의 주요 특징
    • 고속 네트워크 환경에서도 병렬 처리를 통해 성능 저하 없이 트래픽 분석이 가능(멀티 코어 및 멀티 스레드 지원)
    • 기존 Snort 룰을 그대로 사용하면서, 수리카타만의 확장된 룰을 지원
    • 다양한 하드웨어 및 네트워크 가속 기술을 통한 패킷 처리 효율 극대화
    • Lua 언어를 활용하여 복잡한 패킷 분석 및 맞춤형 탐지 로직 구현 가능

Q622회

Snort에서는 대량의 패킷에 대응하기 위하여 Threshold 옵션을 type(임곗값 타입 지정), track(출발지/목적지 IP), count(발생 횟수), seconds(시간)으로 설정할 수 있다. 이 중 threshold type 3가지를 쓰시오.

threshold : type <( ① ) | ( ② ) | ( ③ )>, track <by_src | by_dst>, count <c>, seconds <s>
답과 해설 보기

답: ① limit　② threshold　③ both

  • threshold type은 임곗값의 타입을 지정하고, 방식에는 limit, threshold, both 세 가지가 있음
    • limit — 설정한 시간 내에 최대 N번까지만 경고 발생
    • threshold — N번 발생해야 경고 1번 발생
    • both — N번 발생해야 alert 1번 발생하며, 시간 제한도 적용

다음은 시그니처 기반의 보안 장비 대부분이 적용하고 있는 PCRE(Perl Compatible Regular Expression) 적용 문법을 나타낸 것이다. 질문에 답하시오.

alert tcp any any -> any any (pcre:"/POST.*Content\x2dLength\x3a\x20evilstring/";)
  • ① 해당 Rule은 어떤 문제점이 있는지 서술하시오.
  • ② 해결 방안은 무엇인지 서술하시오.
모범 답안과 해설 보기
모범 답안

① 출발지/목적지 정보가 특정되지 않아(any any) 검사 범위가 너무 넓은 상태에서, 성능 부하가 큰 PCRE 연산을 모든 패킷에 직접 수행하기 때문에 장비 성능에 심각한 영향을 줄 수 있음

② 목적지 IP 주소와 포트를 웹 서버 주소, 80번 포트로 설정하여 부하를 감소하는 방향으로 룰 정책을 변경함

해설
  • 다음은 정규 표현식을 이용해서 페이로드 안의 문자열을 탐지하는 구문
pcre:"/POST.*Content\x2dLength\x3a\x20evilstring/";
  • 슬래시(/)로 둘러싸인 부분이 정규표현식 패턴이고, 마지막 / 뒤의 문자는 PCRE 플래그(옵션)
    • POST — 문자열 "POST"
    • .* — 임의의 문자 0개 이상
    • Content\x2dLength — 문자열 "Content-Length"
    • \x3a — 문자열 ":"
    • \x20 — 문자열 " "(공백)
    • evilstring — 문자열 "evilstring"
  • 출발지/목적지 정보가 특정되지 않아(any any) 검사 범위가 너무 넓은 상태에서, 성능 부하가 큰 PCRE 연산을 모든 패킷에 직접 수행하기 때문에 장비 성능에 심각한 영향을 줄 수 있기 때문에 목적지 IP 주소와 포트를 웹 서버 주소, 80번 포트로 설정하여 부하를 감소하는 방향으로 룰 정책을 변경하는 것이 좋음

  • ① drop/reject 중 어떤 것을 쓰는 것이 좋은지 고르시오.

모범 답안

(1) ① 해당 패킷을 아무 응답 없이 차단하는 옵션　② 해당 패킷을 차단하고, 클라이언트에 ICMP 에러 메시지 응답 또는 TCP RST 전송하는 옵션

(2) ① DROP　② REJECT의 경우 해당 패킷을 차단하고, 클라이언트에 ICMP 에러 메시지를 응답 해주므로 응답 메시지 자체가 공격자에게는 유용한 정보가 될 수 있고, 이를 이용하여 DDoS 공격 등에 악용할 수 있음

  • -j 옵션은 iptables 룰에 매칭될 때 적용할 정책을 지정하는 옵션으로 종류와 특징
    • ACCEPT — 해당 패킷을 허용 / 정상적인 서비스 요청 허용
    • DROP — 해당 패킷을 아무 응답 없이 차단 / 은밀하게 차단하고, 공격자에게 시스템 정보를 노출하지 않음
    • LOG — 패킷을 syslog에 전달하여 기록(/var/log/messages에 저장) / 탐지 및 모니터링, 의심 트래픽을 분석하거나 후속 조치를 위해 기록
    • REJECT — 해당 패킷을 차단하고, 클라이언트에 ICMP 에러 메시지 응답 또는 TCP RST 전송 / 정당한 서비스 요청자에게 명시적으로 차단됨을 알림

  • (3) 스노트 룰의 threshold 옵션은 특정 시간 동안 발생하는 이벤트 수를 제한하여 과도하게 많은 이벤트가 발생하는 것을 막기 위한 옵션이다. 위의 스노트 룰에서 alert 이벤트 발생 수를 제한하는 기준과 방식을 서술하시오.
모범 답안과 해설 보기
모범 답안

(1) ① drop　② reject

(2) depth:13

(3) 같은 출발지(Source IP)에서 1초 동안 같은 이벤트가 10회 이상 발생할 경우 이벤트를 발생

해설
  • action은 패킷의 처리 방식으로 종류
    • alert — 경고를 발생시키고 로그를 남김
    • log — 패킷을 별도로 로그에 기록하고, 경고는 발생하지 않음
    • pass — 패킷을 무시하고 탐지하지 않음
    • drop — 패킷을 차단, 로그를 기록
    • reject — 패킷을 차단, 로그를 기록, 응답 메시지를 전송 (TCP이면 RST 패킷 응답, UDP이면 ICMP Unreachable 메시지 응답)
    • sdrop — 패킷을 차단하지만, 로그를 기록하지 않음
  • 패킷을 차단하고 로그를 기록하는 action은 drop과 reject
  • content 옵션을 통해 패킷의 페이로드 안에 HTTP 1.x 버전으로 루트 페이지(/)에 대한 GET 요청이 포함된 문자열이 있는지 탐지할 수 있음
  • 문자열을 탐지할 때 페이로드의 첫 번째 바이트부터 13번째 바이트 범위 내에서 탐지하기 위해서는 offset:0;은 생략하고, depth:13으로 설정
  • threshold type은 임곗값의 타입을 지정하고, 방식에는 threshold, limit, both 세 가지가 있음
  • threshold
    • 지정된 시간(seconds) 내에 탐지 이벤트가 설정 count 이상으로 발생했을 때 이벤트 발생
    • 이후 같은 조건이 반복되면 다시 이벤트 발생
    • 예: threshold:type threshold, track by_src, count 5, seconds 10;
      → 같은 소스 IP에서 10초 내에 탐지 이벤트가 5번 이상 발생하면 이벤트 발생
      → 그 후 조건이 다시 충족되면 또 이벤트 발생
  • limit
    • 지정된 시간(seconds) 안에 최대 count 개수까지만 이벤트를 발생
    • 초과 탐지는 무시됨 (이벤트 발생 안 함)
    • 예: threshold:type limit, track by_dst, count 3, seconds 60;
      → 같은 목적지 IP에 대해 60초 안에 최대 3번까지만 이벤트 발생
      → 그 이후는 무시되며, 새로운 60초 구간이 시작될 때까지 기다림
  • both
    • threshold와 limit을 동시에 적용
    • count만큼의 이벤트가 seconds 내에 발생해야 이벤트가 발생하고, 이벤트는 그 시간 내에 딱 한 번만 발생함
    • 예: threshold:type both, track by_src, count 10, seconds 5;
      → 같은 소스 IP가 5초 안에 이벤트 10번 발생하면 이벤트는 1회만 발생
      → 이후 동일 조건이 또 충족되면 다음 주기로 다시 이벤트 1회 발생

② FORWARD Chain: 자신을 경유하여 다른 목적지로 전달되는 패킷을 제어하는 체인
③ OUTPUT Chain: 호스트 컴퓨터에서 외부로 나가는 패킷에 대한 제어를 담당하는 체인

(2) TCP 연결을 신규(NEW)로 맺는 패킷의 TCP Flag 값이 SYN이 아닌 경우 [Faked NEW request]를 접두어로 하여 로그에 기록

해설
  • iptables의 룰의 구성 중 Chain
    • INPUT — 호스트 컴퓨터로 향하는 모든 패킷(Inbound)
    • FORWARD — 호스트를 경유하여 다른 곳으로 전달되는 패킷
    • OUTPUT — 호스트 컴퓨터에서 상대측에 보내는 패킷(Outbound)
  • iptables 해당 룰의 상세 의미
    • -A INPUT — 외부에서 방화벽(서버)으로 들어오는 패킷 체인(Chain)의 맨 마지막에 이 규칙을 추가
    • -p tcp — TCP 프로토콜을 사용하는 패킷만을 대상
    • ! --syn — TCP 플래그 중 SYN 비트가 설정되지 않은 패킷
    • -m state — 상태 추적(Connection Tracking) 모듈 사용
    • --state NEW — 방화벽의 연결 추적 테이블에 기록되지 않은, 새로운 연결 시도로 간주되는 패킷
    • -j LOG — 시스템 로그(Syslog)에 기록
    • --log-prefix [Faked NEW request] — 로그 파일에 기록될 때, 식별하기 쉽도록 "[Faked NEW request]"라는 접두어(Prefix) 문구 추가

Q211회

호스트 192.168.1.3으로부터 192.168.10.48로 향하는 비정상적인 트래픽을 감지하였다. 분석을 위해 eth0 인터페이스를 통과하는 패킷 중, IP 주소를 출력할 때 호스트명 대신 IP 주소와 Port 번호로 출력하고 해당 방향의 트래픽만 실시간으로 확인하고자 한다. 이때 사용할 수 있는 tcpdump 명령어를 서술하시오.

모범 답안과 해설 보기
모범 답안

tcpdump -i eth0 -n src host 192.168.1.3 and dst host 192.168.10.48

해설
  • tcpdump 사용법 — tcpdump [옵션] [BPF]
  • 옵션
    • -i — 네트워크 인터페이스를 지정
    • -n, -nn — 출력 시 호스트명 대신 IP 주소와 Port 번호로 출력
    • -v, -vv, -vvv — 패킷을 더 자세하게 출력
    • -w — 지정된 파일로 캡처파일 저장
    • -c — 지정된 개수의 패킷 캡처 후 종료
  • BPF(Berkeley Packet Filter) — 원하는 패킷만을 스니핑하기 위한 룰 지정
    • tcp — TCP 프로토콜 패킷 캡처
    • udp — UDP 프로토콜 패킷 캡처
    • icmp — ICMP 프로토콜 패킷 캡처
    • host — 특정 IP 주소의 트래픽만 보기
    • src host — 해당 IP에서 나가는 패킷만 보기
    • dst host — 해당 IP로 들어오는 패킷만 보기
    • port — 지정된 포트의 트래픽만 보기
