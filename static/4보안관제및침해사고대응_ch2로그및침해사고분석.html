Q15회

다음은 애플리케이션 취약점을 이용한 공격 절차이다. 질문에 답하시오.

  1. 사용자는 해킹된 웹 사이트에 접속한다.
  2. 사용자는 해커가 웹 사이트를 해킹한 후 자동 연결을 위해 삽입한 iframe, 자바스크립트, 리다이렉션(Redirection) 태그에 의해 유포지로 자동 연결된다.
  3. 사용자는 동일한 방식으로 여러 단계의 중간 경유지를 거쳐 최종 유포 사이트로 연결되며, 이는 실제 악성코드 유포 서버를 숨기기 위한 목적이다.
  4. 최종 유포 사이트에서는 사용자 컴퓨터에 존재하는 취약점을 이용하여 악성 코드를 유포한다.
  • (1) 위와 같은 공격 기법 명칭은 무엇인지 쓰시오.
  • (2) 사용자가 실질적으로 악성 코드에 감염되는 곳은 어디인지 쓰시오.
  • (3) 악성 코드 감염을 막기 위해 정적 분석과 동적 분석 방안을 설명하시오.

② 악성 코드를 실제로 실행하여 실행 전후 상태를 분석 및 조사하여 프로그램의 기능을 파악하는 방법

  • 제시된 절차에서 악성 코드에 실제 감염되는 곳은 최종 유포사이트를 통해서 취약점을 이용해 악성코드 감염이 됨
  • 정적 분석 — 의심되는 실행(PE) 파일을 실행하지 않고, 파일 자체가 가지고 있는 바이너리의 구조와 코드 내용을 분석하는 방법

Q425회

윈도우 PE(Portable Executable) 파일은 윈도우 7과 같이 NT 계열 운영체제에서 실행 가능한 파일 포맷이다. PE 파일은 실행 코드, 데이터, 리소스 및 메타데이터를 포함하는 구조를 가지며, 일반적으로 .exe(executable), .dll(dynamic link library), .sys(driver) 확장자를 가진 파일들을 포함한다. 악성 파일의 경우에도 윈도우 OS에서 실행되기 위해 PE포맷을 사용하는데, 악성 코드 작성자는 PE 파일을 난독화하거나, PE 헤더와 섹션 정보를 변형하여 디버깅 및 분석을 어렵게 만든다. 이러한 악성 파일을 분석하는 3가지 방법에 대하여 서술하시오.

모범 답안과 해설 보기
모범 답안

① 의심되는 실행(PE) 파일을 실행하지 않고, 파일 자체가 가지고 있는 바이너리의 구조와 코드 내용을 분석하는 방법

② 악성 코드를 실제로 실행하여 실행 전후 상태를 분석 및 조사하여 프로그램의 기능을 파악하는 방법

③ 자동화 도구를 통해 정적 분석과 동적 분석을 결합하여 악성 코드의 전체적인 흐름을 파악하는 분석 방법

해설
  • 정적 분석 — 의심되는 실행(PE) 파일을 실행하지 않고, 파일 자체가 가지고 있는 바이너리의 구조와 코드 내용을 분석하는 방법
  • 동적 분석 — 악성 코드를 실제로 실행하여 실행 전후 상태를 분석 및 조사하여 프로그램의 기능을 파악하는 방법
  • 자동화 분석 — 자동화 도구를 통해 정적 분석과 동적 분석을 결합하여 악성 코드의 전체적인 흐름을 파악하는 분석 방법

Q12회

HTTP GET Flooding 공격은 서비스 거부(DoS 또는 DDoS) 공격 유형 중 하나로, 웹 서버의 자원을 고갈시켜 정상적인 사용자 요청을 처리하지 못하게 만드는 공격이다. 특히 HTTP GET 요청을 반복적으로 대량 전송하여 웹 접속 요청을 폭주시켜 세션 자원을 소진하게 만드는 공격이다. 다음은 HTTP GET Flooding 공격에 대한 스노트(Snort) 룰(rule)이다. 이 스노트 룰을 참조하여 각각의 질문에 답하시오.

alert tcp any any -> any 80 (msg:"HTTP Get Flooding Detect"; content:"GET / HTTP/1."; nocase; threshold:type threshold, track by_src, count 10, seconds 1; sid:10009999;)
  • ① 해당 룰에서 탐지 시 출력되는 메시지명을 쓰시오.
  • ② 스노트 룰에서 nocase가 의미하는 것은 무엇인지 서술하시오.
  • ③ content: "GET / HTTP/1."가 의미하는 것은 무엇인지 서술하시오.
  • ④ 스노트 룰의 threshold 옵션은 특정 시간 동안 발생하는 이벤트 수를 제한하여 과도하게 많은 이벤트가 발생하는 것을 방지하기 위한 옵션이다. threshold:type threshold, track by_src, count 10, seconds 1이 의미하는 것을 서술하시오.
모범 답안과 해설 보기
모범 답안

① HTTP Get Flooding Detect

② content 검사 시 대소문자 구분 없이 검색하도록 설정하는 옵션이다.

③ HTTP 1.x 버전으로 루트 페이지(/)에 대한 GET 요청이 포함된 패킷을 탐지하도록 룰(rule)을 설정했다는 의미이다.

④ 같은 출발지(Source IP)에서 1초 동안에 탐지 이벤트가 10번 이상 발생했을 때 알림 설정(alert action)을 수행한다는 의미이다.

해설
  • alert tcp — TCP 패킷을 탐지하여 경고
  • any any -> any 80 — 모든 출발지에서 단방향(출발지 -> 목적지)으로 향하는 목적지 HTTP(80) 검사
  • content:"GET / HTTP/1."; nocase; depth 13; — 패킷 내 첫 번째 바이트부터 13번째 까지 범위 내 문자열 GET / HTTP/1.가 포함되어야 하며, 대소문자 구분없이 매칭

① Smurf 공격

② ICMP Echo Request 패킷을 특정 네트워크의 브로드캐스트(Broadcast) 주소로 전송한다. 이로 인해 해당 네트워크 내의 다수의 호스트가 동시에 ICMP Echo Reply 패킷을 공격 대상에게 전송하게 되며, 결과적으로 공격 대상 시스템에는 대량의 응답 패킷이 집중되어 부하가 급격히 증가

③ 라우터에서 Directed Broadcast를 차단하고, 호스트가 브로드캐스트 주소로 수신된 ICMP 요청에 대해 응답하지 않도록 설정

Smurf 공격의 공격 원리
  • 공격자는 공격 대상 호스트의 IP 주소로 위장하여 ICMP Echo Request를 특정 IP 브로드캐스트(Broadcast) 주소로 보내게 됨
  • 공격 대상 IP 주소로 소스 IP 주소를 설정하고 ICMP Echo Request 패킷을 브로드캐스트로 다수의 시스템에 전송하면 공격 대상 서버는 ICMP Echo Reply 패킷들을 동시다발적으로 수신하여 시스템 성능에 문제를 일으키게 됨
  • 스머프 공격은 바운스(Bounce) 사이트라고 불리는 제3의 사이트를 이용해서 공격
Smurf 공격의 대응 방법
  • 중간 매개지로 쓰이는 것을 막기 위해서 라우터에서 다른 네트워크로부터 자신의 네트워크로 들어오는 브로드캐스트 패킷(Directed Broadcast)을 막도록 설정
  • 호스트는 브로드캐스트 주소로 전송된 ICMP 패킷에 대해 응답하지 않도록 시스템을 설정
  • 침입 차단 시스템(IPS)을 통해서 많은 수의 같은 ICMP Echo Reply 패킷이 전송되면 차단되도록 설정

① 하트블리드(HeartBleed)

② 영향을 받지 않는 버전으로 OpenSSL 업데이트

③ Heartbeat 서비스 여부를 판단하여 불필요 시 제거

해설
  • 하트 블리드는 OpenSSL 암호화 라이브러리의 하트비트(Heartbeat)라는 확장 모듈에서 클라이언트 요청 메시지를 처리할 때 데이터 길이 미검증으로 64KB 크기의 데이터를 외부에서 제한 없이 탈취할 수 있는 취약점
  • 취약한 버전과 안전한 버전
    • 취약한 버전 — OpenSSL 1.0.1 ~ OpenSSL 1.0.1f, OpenSSL 1.0.2-beta, OpenSSL 1.0.2-beta1
    • 안전한 버전 — OpenSSL 1.0.1g, OpenSSL 1.0.0 버전, OpenSSL 0.9.8 버전
  • 대응 방법
    • 버전 업데이트 — 영향을 받지 않는 버전으로 OpenSSL 업데이트
    • Heartbeat Rule 탐지 — IDS 및 IPS에서 Heartbeat Request에서 Request 페이로드의 길이(Payload Length) 필드와 실제 데이터 길이 간의 불일치를 확인
    • 소스코드 확인 — ssl/d1_both.c 파일 확인하여 취약점이 존재하는지 여부를 확인하여 커스터마이징이 된 부분은 직접 소스 코드를 수정
    • Heartbeat 활성화 확인 — OpenSSL에서 Heartbeat 서비스가 불필요할 경우 비활성화
    • SSL 인증서 업데이트 — 서버 측 비밀키가 유출됐을 경우, 인증서를 재발급
    • 비밀번호 재설정 — 사용자 계정 탈취의 위험성에 따라 비밀번호 재설정
  • 시스템적으로 하트블리드의 대응방안
    • 버전 업데이트 — 영향을 받지 않는 버전으로 OpenSSL 업데이트
    • 소스코드 확인 — ssl/d1_both.c 파일 확인하여 취약점이 존재하는지 여부를 확인하여 커스터마이징이 된 부분은 직접 소스 코드를 수정
  • 서비스적으로 하트블리드의 대응방안
    • 불필요한 서비스 제거 — Heartbeat 서비스 여부를 판단하여 불필요 시 제거
    • SSL 인증서 업데이트 — 서버 측 비밀키가 유출됐을 경우, 인증서를 재발급
    • 비밀번호 재설정 — 사용자 계정 탈취의 위험성에 따라 비밀번호 재설정
